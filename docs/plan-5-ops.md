# 计划 5：运维

> 状态：设计已锁定，待开工
> 依赖：计划 1~4

## 平台硬约束：bot 不能主动说话

QQ 官方机器人的主动消息有严格配额（群聊基础档每月 4 条），
所以系统**只能被动回答**，无法主动播报、无法自我告警。

推论：**所有沉默失败都无法被自动发现。**
上次「判题静默」事故就是这么被眼睛发现的，下次也一样——除非设计上避免沉默失败。

## 决定 1：没有任何后台定时任务

最终流程里不存在定时器：`new` 派题、AC/`g` 关题，全部由用户消息驱动。

```
❌ while True: await asyncio.sleep(...)   ← 一个都不需要
✅ 所有状态变更由指令触发，天然无「后台任务挂掉」这类沉默失败
```

唯一需要后台做的是**题库预屯**（见决定 2），它失败也不影响正常游戏——
底仓还在，只是不再增长。日志会记录，`r` 里能看出泳位。

## 决定 2：题库预屯（方案 C，A+B 合并）

```
底仓   启动时保证库内 ≥200 道可选题（未则后台补爬）
补充   之后每天补 20 道，保持水位
派题   只从 cf_cache.db 里选，不实时抓
```

好处：cloudscraper 失效时，已屯的题够玩几周，游戏不停摆。

成本：500 题 × 2 秒 ≈ 17 分钟一次性爬取。

## 决定 3：健康信息 piggyback

bot 不能主动播报，那就在**用户主动查时**顺带暴露：

- `r`（排行榜）输出末尾附一行健康摘要：题库余量、群当前难度档、上次抓取成功时间
- `status` 指令（已有）扩展，加入 rating 轮次状态

这样群友每天看榜时都会看到「题库剩 183 道」，异常时一眼就能注意到。

## 残留风险

| 风险 | 严重度 | 缓解 |
|---|---|---|
| cloudscraper 被 CF 封 | 中 | 底仓 200+ 题撑几周；失效时日志报错，`r` 里显示抓取失败时间 |
| 长时间无人 `new`，游戏暂停 | 无 | 这是设计意图，不是故障 |
| QQ 图片上传频率限制（每 `q` 两张图） | 中 | 未验证，需实测 |
| SQLite WAL 备份不一致 | 低 | 用 `sqlite3 .backup`，不要直接 cp |
| 数据卷丢失 | 中 | 用户自行备份 `data/` 目录 |
